# Server Hardening

**Одна команда превращает свежий VPS на Debian или Ubuntu в сервер, который пускает только по вашему ключу, — и не закроет старую дверь, пока вы не прошли через новую.**

Один bash-скрипт, который запускается один раз от root на новом сервере. Он задаёт
несколько вопросов, создаёт sudo-пользователя с вашим SSH-ключом, переносит SSH на новый
порт со входом только по ключу и без root, включает firewall, fail2ban и по желанию
CrowdSec, усиливает ядро, включает автообновления безопасности и журнал аудита, заменяет
приветствие при входе короткой сводкой о сервере, умеет слать уведомления в Telegram и в
конце запускает аудит Lynis. Позже `sudo harden --check` проверит сервер, ничего не меняя.
Интерфейс — на русском и английском.

```bash
curl -fsSLo harden.sh https://github.com/N0deZ3r0/server-hardening/releases/download/v2026.10.27/harden.sh && echo "1f5ae59abadc034e57a63da958e941f0f7d70c1baa123c6ece0f8d8407a0d9d2  harden.sh" | sha256sum -c - && sudo bash harden.sh
```

Команда скачивает конкретный релиз и сверяет его SHA-256 до запуска: если отличается хоть
один байт, `sha256sum` обрывает цепочку и ничего не выполняется. Что это доказывает, а что
нет — в разделе [Релизы и проверка](#релизы-и-проверка).

В некоторых минимальных образах нет двух программ, которые нужны самой команде. Вы вошли
как root и получили `sudo: command not found`? Запустите последнюю часть без него:
`bash harden.sh`. Нет `curl`? Сначала `apt update && apt install -y curl`. Обе программы
скрипт потом поставит сам.

## Сначала — честно про то, от чего это защищает

**Реально не пускает посторонних только вход по ключу.** После настройки сервер вообще не
принимает пароль по SSH — ни для root, ни для кого. Подбирать бессмысленно: нужен ваш
закрытый ключ.

**Всё остальное снижает шум и ущерб.** Новый порт убирает из логов ботов, которые
стучатся только в 22, но любой, кто сканирует, найдёт его за секунды — это не замок.
fail2ban и CrowdSec банят адреса, которые продолжают пробовать. Настройки ядра, AppArmor и
auditd мешают развить взлом и помогают потом понять, что произошло. Автообновления
закрывают известные дыры, не дожидаясь вас.

**Ничто из этого не поможет**, если украдут закрытый ключ с вашего компьютера, если позже
вы поставите веб-приложение с уязвимостью или если взломают самого хостера. Это и есть
реальные способы потерять сервер, и скрипт до них не дотягивается.

## Он не закроет вам доступ

Потерять доступ к удалённому серверу — единственная ошибка, которую нельзя исправить
снаружи, поэтому большая часть скрипта посвящена тому, чтобы её не совершить.

- **Старый порт SSH остаётся открытым, пока вы не докажете, что новый работает.** Скрипт
  запускает SSH на обоих портах, показывает точную команду и ждёт, пока вы войдёте из
  *второго* окна. Старый порт закрывает только ответ «да». Ответ «нет» возвращает SSH
  ровно в исходное состояние.
  До этого на старом порту действуют прежние правила входа — новые относятся только к новому
  порту, — так что ключ, который не подошёл, ничего не стоит, даже если сессия оборвётся.
  На сервере, который этот скрипт уже настраивал, «прежние правила» — это правила прошлой
  настройки, а не хостера. И «да» нужно набрать после того, как вопрос появился на экране:
  клавиша, нажатая, пока ставились пакеты, отбрасывается, а не становится ответом.
- **Ваш IP попадает в белый список** fail2ban, CrowdSec и лимита firewall — по вашему
  согласию. Без этого пара быстрых тестовых входов банит самого администратора (так и
  случилось во время проверки).
- **Старые аккаунты** (`ubuntu`, `opc`, `admin` от хостера) блокируются только *после*
  того, как вход под новым пользователем подтверждён: на AWS или Oracle вы работаете
  именно под ними. Если вы их оставляете, скрипт говорит, что SSH будет пускать только
  нового пользователя, и спрашивает, пускать ли и их, — молча он их не отрезает.
- **Работает внутри tmux.** Свежие образы VPS часто перезапускают SSH в первые минуты и
  обрывают сессию; настройка продолжается, а `tmux attach -t harden` возвращает вас к ней.
- **Ждёт хостера.** Многие образы после первой загрузки делают через cloud-init полное
  обновление — вместе с GRUB и ядром — 5–20 минут. Перезагрузка посреди этого однажды
  оставила тестовый сервер незагружаемым, поэтому скрипт ждёт, а перед своей
  перезагрузкой проверяет, что никакие пакеты не ставятся.
- **Пароль root не блокируется**, если у нового пользователя нет пароля, — иначе sudo был
  бы недоступен.
- Каждый файл, который скрипт заменяет или правит, сначала копируется в `/root/harden-backup-<дата>/`.
- **Ваши собственные jail'ы fail2ban остаются.** Свои два jail'а для SSH скрипт пишет в
  отдельный файл в `jail.d`, а существующий `jail.local` не трогает.

## Что спрашивает

1. Язык интерфейса (English / Русский) — спрашивается один раз и запоминается; сменить: `sudo harden --lang`
2. Имя нового sudo-пользователя
3. Публичный SSH-ключ — вставить, загрузить с `github.com/<ник>.keys` или взять у root
4. Новый порт SSH (предлагает случайный)
5. Какие ещё порты открыть, например `80,443`
6. Добавлять ли ваш текущий IP в белый список
7. Ночная перезагрузка после обновления ядра, блокировка root и других аккаунтов — а если
   они остаются, сохранить ли им вход по SSH, — CrowdSec, Lynis
8. Уведомления в Telegram — если да, скрипт проведёт через создание бота
9. Отключить ли ответ на ping (по умолчанию — нет)

Затем — пароль для нового пользователя: он нужен для sudo.

У каждого вопроса «да/нет» одна и та же подсказка, и в ней словами сказано, что значит
просто Enter: `[y/n, Enter — да]` или `[y/n, Enter — нет]`. Понимаются `y`, `yes`, `д`, `да`
и `n`, `no`, `н`, `нет`; на любой другой ответ вопрос задаётся заново, а не считается за «нет».

## Что делает

| Область | Что меняется |
|---|---|
| **SSH** | Новый порт, `AuthenticationMethods publickey`, пароли выключены, `PermitRootLogin no`, `AllowUsers <вы>` (плюс аккаунты, которые вы назовёте), `sshd_config` читает только root, постквантовый обмен ключами в приоритете (`mlkem768x25519`, `sntrup761x25519` — что поддерживает установленный OpenSSH), без слабых шифров, MAC, DH-групп и хост-ключей, без проброса портов, `MaxAuthTries 3`, версия скрыта |
| **Аккаунты** | sudo-пользователь с вашим ключом, политика паролей (от 12 символов, 3 типа), журнал всех команд sudo, пароль root заблокирован, аккаунты хостера заблокированы вместе с их правилами `NOPASSWD` |
| **Firewall** | UFW: всё входящее запрещено, кроме SSH; на SSH лимит подключений для всех, кроме вашего IP; по желанию — без ответа на ping |
| **Подбор паролей** | fail2ban (`sshd` aggressive + `recidive`, бан растёт до 4 недель), по желанию CrowdSec с nftables-bouncer |
| **Ядро** | `kptr_restrict`, `dmesg_restrict`, защита BPF, `ptrace_scope`, защищённые ссылки и FIFO, фильтры подмены адресов и редиректов, SYN cookies, BBR; ненужные файловые системы и протоколы (dccp, sctp, rds, tipc) отключены |
| **Аудит** | правила auditd на аккаунты, sudoers, конфиг SSH, cron, модули ядра, время, команды от root; учёт процессов; sysstat |
| **Обновления** | unattended-upgrades для обновлений безопасности, needrestart, ночная перезагрузка по желанию; при обновлении сохраняются локальные конфиги (`--force-confold`), поэтому пакет, чей конфиг правил скрипт, не задерживается |
| **Система** | AppArmor, chrony, постоянный журнал с лимитом размера, без core dump (apport выключен), `UMASK 027`, свой `/tmp` у каждого пользователя (libpam-tmpdir), ModemManager и udisks2 выключены, юридический баннер до входа, имя сервера в `/etc/hosts` |
| **Вход** | Стандартное приветствие Ubuntu (Welcome, ESM, реклама, лицензия) заменено на `server-status` |
| **Уведомления** | По желанию — сообщения в Telegram: каждый вход по SSH, падение защитной службы, загрузка, ежедневная сводка |
| **Отчёт** | Аудит Lynis, отчёт в `/root/harden-report.txt`, лог в `/var/log/harden.log`; скрипт остаётся как `/usr/local/sbin/harden` для `--check` |

## Сводка при входе

Показывается один раз за SSH-сессию (не повторяется в каждом окне tmux) и доступна в любой
момент командой `server-status`:

```
========================================
       🖥️  SYSTEM STATUS
========================================
 IP: 203.0.113.10
 Hostname: my-server
 OS: Ubuntu 24.04.5 LTS (6.8.0-142-generic)
 User: sysop
 Loadavg: 0.08 0.05 0.01
 Uptime: 3 days, 4 hours
 Updates: 0
----------------------------------------
 CPU: 2 cores
 RAM: 1967 MB total, 1447 MB free (73%)
 Disk /: 29G total, 26G free (89%)
 Gateway: 203.0.113.1
----------------------------------------
 ufw        ✓
 ssh        ✓
 fail2ban   ✓
 crowdsec   ✓
 auditd     ✓
========================================
```

Показываются только установленные службы (nginx, x-ui и docker появятся, когда будут).
Число обновлений берётся из кэша Ubuntu, поэтому вход не ждёт apt. Строка
`Reboot: required` появляется, когда ждёт новое ядро; свободные RAM и диск желтеют ниже
25% и краснеют ниже 10%.

Стандартное приветствие отключается через `dpkg-statoverride`, а не через `chmod` или
правку файлов: такая настройка переживает обновления пакетов, а обычный `chmod` слетает при
следующем обновлении пакета.

На сервере, настроенном более старой версией: `sudo bash harden.sh --install-status`.

## Уведомления в Telegram

По желанию, вопрос задаётся при настройке; на уже настроенном сервере —
`sudo harden --setup-telegram`. Бота создавайте в https://t.me/BotFather — официальном, с
синей галочкой: поиск по имени выдаёт подделки. Скрипт проверяет токен бота у Telegram, сам
находит ваш
chat id, когда вы нажмёте Start в боте, и присылает тестовое сообщение — вы подтверждаете,
что оно пришло, и только потом что-либо устанавливается.

| Уведомление | Когда |
|---|---|
| 🔑 вход по SSH | каждый успешный вход — пользователь, IP, тип и отпечаток ключа; соединения с теми же тремя в течение 3 с приходят одним сообщением с пометкой `×2` (MobaXterm, WinSCP и подобные открывают второе соединение для файлов) |
| ❌ служба упала | `ssh`, `fail2ban`, `crowdsec`, его bouncer, `auditd` или `unattended-upgrades` завершились с ошибкой |
| 🔄 сервер запущен | после каждой загрузки, с версией ядра |
| 📊 ежедневная сводка | 09:00 по времени сервера: обновления, нужна ли перезагрузка, входы и баны за сутки, упавшие службы, диск и память |

Главное уведомление — вход, которого вы не делали; остальные сообщают, что серверу нужно
внимание, раньше, чем вы сами на него зайдёте.

Как это устроено и почему:

- **Входы читаются из журнала** небольшой службой, поэтому ни PAM, ни `sshd_config` не
  правятся.
- **Уведомления о падениях — это drop-in файлы systemd с `OnFailure=`**: собственные файлы
  скрипта рядом с юнитами, убираются простым удалением.
- **Токен бота** хранится в `/etc/harden/telegram.conf`, доступном только root, и передаётся
  curl через stdin. Он не появляется в командной строке, где его мог бы прочитать через `ps`
  любой локальный пользователь, и не записан ни в один скрипт или юнит. CI проверяет и то,
  и другое.
- Отдельные баны fail2ban **не** отправляются: публичный сервер набирает их десятки в день.
  Они считаются в ежедневной сводке.

После установки более новой версии `harden` выполните `sudo harden --setup-telegram` ещё раз
и ответьте «да» на вопрос «Использовать уже сохранённого бота?» — служебные скрипты
заменятся и перезапустятся, токен заново вводить не нужно.

Отключить: `sudo systemctl disable --now harden-login-watch harden-daily-report.timer
harden-boot-alert && sudo rm /etc/harden/telegram.conf`.

## Проверка сервера

```bash
sudo harden --check          # или: sudo bash harden.sh --check
```

Ничего не меняет — даже каталога не создаёт. Читает действующую конфигурацию SSH
(`sshd -T`), аккаунты и правила sudo, firewall, fail2ban и CrowdSec, auditd, AppArmor,
обновления, время и параметры ядра и выводит по строке на каждый пункт. На сервере,
который настраивал этот скрипт, каждое записанное им значение ядра сверяется с
действующим, так что параметр, который что-то вернуло обратно, будет виден. Перечисляются и
конфиги пакетов, которые обновление отложило для просмотра. Другой firewall вместо UFW —
firewalld либо nftables или iptables, отбрасывающие входящие, — распознаётся и отмечается
`!`; его правила не читаются. Там, где посмотреть нельзя —
контейнер не даёт прочитать конфигурацию SSH, не создавая каталог, — проверка так и пишет
с `!`, а не объявляет конфигурацию сломанной. Пример формата:

```
SSH
  ✓ Порт 10022
  ✓ PermitRootLogin no
  ✓ PasswordAuthentication no
  ✓ Постквантовый обмен ключами
  ✓ Нет слабых алгоритмов
Аккаунты
  ✓ Пароль root заблокирован
  ! sudo без пароля (NOPASSWD): deploy
Сеть и защита
  ✓ UFW включён, входящие запрещены
  · Порты, слушающие снаружи: 80 443 10022
  ✗ fail2ban не защищает SSH
...
Итог: ✓ 21  ! 2  ✗ 1
```

`✗` — то, что пускает посторонних или оставляет незакрытые дыры; `!` — стоит посмотреть; `·` — факт
без оценки: какие порты должны быть открыты, решаете вы, проверка их только перечисляет.
Код выхода равен 1, если есть хоть один `✗`, так что проверку можно запускать из cron или
мониторинга. Работает и на серверах, которые этот скрипт не настраивал, — в этом и смысл:
быстрый ответ на вопрос «в каком состоянии эта машина».

## Запуск без вопросов

Любой ответ можно задать заранее. Проверка входа на новом порту всё равно спрашивается —
это единственный шаг, который нельзя пропускать.

```bash
sudo HARDEN_LANG=ru NEW_USER=sysop SSH_PORT=42222 GITHUB_KEYS_USER=вашник \
     EXTRA_PORTS=80,443 ADMIN_IP=203.0.113.5 AUTO_REBOOT=yes LOCK_ROOT=yes \
     LOCK_OTHER_USERS=yes INSTALL_CROWDSEC=no RUN_LYNIS=yes REBOOT_NOW=no bash harden.sh
```

| Переменная | Значение |
|---|---|
| `HARDEN_LANG` | `ru` или `en`; без неё скрипт спросит один раз и запомнит ответ |
| `NEW_USER`, `SSH_PORT` | новый пользователь и порт |
| `SSH_PUBKEY` / `GITHUB_KEYS_USER` | сам ключ или ник на GitHub, откуда взять ключи |
| `EXTRA_PORTS` | через запятую, `80,443` или `51820/udp` |
| `ADMIN_IP` | IP для белого списка; пусто — без него |
| `AUTO_REBOOT`, `REBOOT_TIME` | ночная перезагрузка после обновления ядра, по умолчанию `04:00` |
| `LOCK_ROOT`, `LOCK_OTHER_USERS` | заблокировать пароль root / аккаунты хостера |
| `SSH_EXTRA_USERS` | существующие аккаунты, которым оставить вход по SSH кроме нового пользователя, `"deploy monitoring"`; пусто — никому |
| `INSTALL_CROWDSEC`, `RUN_LYNIS`, `REBOOT_NOW`, `SERVER_STATUS` | `yes` / `no` |
| `REUSE_USER` | `yes` — использовать уже существующий аккаунт (иначе спросит) |
| `TELEGRAM`, `TG_CHAT_ID`, `TG_REPORT_TIME` | `yes` / `no`, чат для сообщений, время ежедневной сводки (`09:00`) |
| `DISABLE_PING` | `yes` — не отвечать на ping (ICMP echo); по умолчанию `no` |
| `TG_TOKEN` | токен бота; в tmux не передаётся (был бы виден в `ps`), поэтому там спрашивается заново со скрытым вводом |
| `SET_USER_PASSWORD=no` | не задавать пароль для sudo сейчас; root тогда не блокируется |

## Совместимость

| | |
|---|---|
| ОС | Debian 12/13, Ubuntu 22.04/24.04/26.04. RHEL, Alma, Rocky и CentOS не поддерживаются |
| Виртуализация | KVM, VMware, Hyper-V, Xen — полностью. LXC/OpenVZ — частично: auditd, AppArmor и часть sysctl пропускаются |
| Архитектура | x86_64 и ARM64 |
| Проверено вживую | Ubuntu 24.04.5, KVM (OpenStack с cloud-init), 2 vCPU / 2 ГБ: полный прогон с чистого образа на версиях 2026.10.7 (Lynis 78 → 84, после перезагрузки 86) и 2026.10.19; про версии между ними — в разделе «Ограничения» |
| Проверяется в CI | при каждом изменении: вся настройка на виртуальной машине каждой из пяти версий — загрузка облачного образа, ответы на вопросы в терминале, проверка входа снаружи, затем перезагрузка, `--refresh`, повторный запуск и `--undo`; плюс части настройки на Ubuntu 24.04 и `--check` в контейнерах |

**У облачных хостеров** (AWS, Oracle, Hetzner Cloud, GCP, Azure) есть свой firewall в
панели. Откройте там новый порт SSH *до* того, как подтверждать вход. Если забыть, проверка
не пройдёт, вы ответите «нет», и SSH откатится.

**Oracle Cloud:** образы Ubuntu содержат свои правила iptables, которые конфликтуют с UFW.
Удалите их заранее: `sudo apt purge -y iptables-persistent netfilter-persistent`.

## После настройки

```bash
ssh -p <порт> <пользователь>@<сервер>   # теперь только так
sudo ufw allow 443/tcp                 # открыть порт
sudo fail2ban-client status sshd       # забаненные адреса
sudo cscli decisions list              # баны CrowdSec
sudo ausearch -k identity -i           # кто менял аккаунты
sudo lynis audit system                # полный аудит
server-status                          # сводка
sudo harden --check                    # проверка, ничего не меняется
sudo harden --setup-telegram           # подключить уведомления
sudo harden --ping off                 # не отвечать на ping (--ping on — вернуть)
sudo harden --lang en                  # сменить запомненный язык (ru или en)
sudo harden --refresh                  # применить настройки новой версии, без вопросов
sudo harden --answers                  # команда, которая повторяет эту настройку
sudo harden --undo                     # откатить настройку из резервной копии
```

Как откатить часть настроек: SSH — в `/etc/ssh/sshd_config.d/00-hardening.conf`, ядро — в
`/etc/sysctl.d/99-hardening.conf` и `99-protect-links.conf`, исходные файлы — в `/root/harden-backup-<дата>/`.
Заблокированный аккаунт возвращается командой `sudo usermod -U -s /bin/bash <имя>`.

## Если это VPN-сервер

Про VPN настройка ничего не знает: после неё сервер принимает SSH и больше ничего. Что VPN
нужно сверх этого — ничто из перечисленного тестами проекта не проверяется:

- **Откройте порт VPN, и только его:** `sudo ufw allow 51820/udp` для WireGuard,
  `sudo ufw allow 443/tcp` для прокси на 443. Порт панели управления лучше открыть только
  своему адресу: `sudo ufw allow from <ваш IP> to any port <порт> proto tcp`.
- **Прокси** (Xray, sing-box, Shadowsocks, панели вроде x-ui) больше ничего не требует: он
  принимает подключения и сам устанавливает свои.
- **Маршрутизируемому VPN** (WireGuard, OpenVPN) нужна ещё пересылка пакетов. Ядро её не
  делает, пока не сказано, а firewall по умолчанию запрещает:

  ```bash
  echo 'net.ipv4.ip_forward = 1' | sudo tee /etc/sysctl.d/99-vpn.conf && sudo sysctl --system
  sudo ufw route allow in on wg0 out on eth0
  ```

  с вашими именами интерфейсов. Трансляцию адресов (`MASQUERADE`) обычно добавляет `PostUp`
  самого VPN.
- **SSH-туннели выключены** (`AllowTcpForwarding no`) — как включить, сказано в «Ограничениях».
- **Контейнеры публикуют порты в обход UFW** — см. «Ограничения».
- **Не отвечать на ping** — опция как раз для этого случая; что она скрывает и чего не
  скрывает, сказано в «Ограничениях».
- После установки VPN посмотрите строку «Порты, слушающие снаружи» в `sudo harden --check`:
  там должны быть порт SSH, порт VPN и ничего неожиданного.

## Обновление

На уже настроенном сервере скачайте новый скрипт и дайте ему применить свои настройки —
те же загрузка и контрольная сумма, а вместо настройки `--refresh`:

```bash
curl -fsSLo harden.sh https://github.com/N0deZ3r0/server-hardening/releases/download/v2026.10.27/harden.sh && echo "1f5ae59abadc034e57a63da958e941f0f7d70c1baa123c6ece0f8d8407a0d9d2  harden.sh" | sha256sum -c - && sudo bash harden.sh --refresh
```

`--refresh` ничего не спрашивает. Он записывает настройки ядра, правила аудита, настройки
автообновлений, jail'ы fail2ban, сводку при входе и помощников Telegram так, как это делает
эта версия, и заменяет установленный `harden`. Аккаунты, SSH и firewall не трогаются: это
те части, где ошибка стоит доступа, и меняет их только полная настройка с её проверкой
входа. То, что вы переключили руками после настройки, остаётся как есть: `--ping`, хук
сводки при входе, если вы его удалили, время ежедневной сводки. Что после этого ещё
отличается, покажет `sudo harden --check`.

## Повторить настройку и откатить её

Ответы настройки хранятся на сервере в `/etc/harden/setup.conf` — без секретов: токен бота
лежит отдельно, пароль не хранится нигде. Итоговый отчёт печатает команду, которая повторяет
настройку с теми же ответами, а `sudo harden --answers` печатает её снова. Если сервер часто
переустанавливается, сохраните её у себя, не на сервере. Пароль нового пользователя, токен
бота и проверка входа спрашиваются всё равно.

`sudo harden --undo` откатывает настройку из самой старой резервной копии в
`/root/harden-backup-*` — сделанной до первого запуска. Возвращаются SSH (порт и способы
входа), firewall, root, заблокированные аккаунты и системные файлы, которые настройка
заменила; все добавленные ею файлы удаляются, а отключённые ею службы включаются снова.
Установленные пакеты и созданный пользователь
остаются; параметры ядра вернутся после перезагрузки. fail2ban останавливается, если до
настройки у него не было своей конфигурации: на настройках по умолчанию у него нет исключения
для вашего адреса, и банит он по тому, что уже есть в логе. Команда спрашивает подтверждение, а
окно, в котором она запущена, не обрывается — проверьте вход по-старому, прежде чем его
закрыть.

## Релизы и проверка

Скрипт, который запускается от root, должен быть именно тем, который вы собирались
запустить. Каждая версия публикуется как
[релиз](https://github.com/N0deZ3r0/server-hardening/releases) с `harden.sh`, `SHA256SUMS` и
подписанной записью о происхождении сборки, а команда установки выше называет один релиз и
одну контрольную сумму.

Что менялось в каждой версии и какие версии где-то не заработали — в
[CHANGELOG.ru.md](CHANGELOG.ru.md); текст каждого релиза собирается из него. Релиз не
публикуется, если CI — а в него входит вся настройка на виртуальной машине каждой
поддерживаемой версии — не прошёл для его коммита.

**Что доказывает контрольная сумма:** скачанный файл байт в байт совпадает с выпущенным —
не обрезан, не изменён по дороге и не является тем, что сегодня случайно лежит в `main`.
Релиз публикуется, только если тег, версия внутри скрипта и контрольная сумма в этом README
совпадают, и только из коммита в `main`, прошедшего проверки.

**Чего она не доказывает:** что сам релиз честный. Контрольная сумма лежит в том же
репозитории, что и скрипт, и тот, кто захватил бы аккаунт GitHub, мог бы поменять и то, и
другое. Это сужают три вещи:

- **Релизы неизменяемы.** Начиная с 2026.10.22 опубликованный релиз нельзя изменить:
  GitHub не даёт передвинуть его тег или заменить файлы — владельцу аккаунта тоже. На что
  номер версии указывал вчера, на то он указывает и сегодня. Более ранние релизы
  опубликованы до включения этой настройки.
- **Происхождение.** С GitHub CLI команда `gh attestation verify harden.sh --repo
  N0deZ3r0/server-hardening` показывает, из какого коммита и каким workflow собран файл, с
  подписью через Sigstore, — файл, собранный где-то ещё, проверку не пройдёт.
- **Своя копия контрольной суммы.** Прочитайте скрипт один раз, запишите контрольную сумму
  прочитанной версии и пользуйтесь именно этой командой. Она будет ставить то, что вы
  проверили.

Самый свежий невыпущенный код — в `main`:
`curl -fsSL https://raw.githubusercontent.com/N0deZ3r0/server-hardening/main/harden.sh -o harden.sh`
— без контрольной суммы для сверки; это для разработки, а не для серверов.

## Ограничения

Оставлено сознательно, с причиной для каждого:

- **Человеком запускалось на одной системе, в CI — на пяти.** Человек запускал настройку
  только на Ubuntu 24.04 (KVM, один хостер) — версию 2026.10.26 там провели через весь цикл:
  настройка, обрыв связи на вопросе о входе, `--undo`, вторая настройка, перезагрузка. CI
  запускает её целиком на виртуальной машине
  каждой поддерживаемой версии ([tools/e2e.py](tools/e2e.py)). Первый же такой прогон
  показал, что на Ubuntu 26.04 настройка не работала никогда — sudo там это sudo-rs, и одну
  из записываемых настроек он не знает, — а на Debian 12 перестала работать в версии
  2026.10.15 из-за опции `cp`, сломанной в coreutils этого выпуска. Обе системы значились
  поддерживаемыми. Чего прогоны на ВМ не покрывают: сам Telegram (уведомления уходят на
  подставной API), Lynis, IPv6, повторную настройку с другим пользователем и всё, чем образ
  настоящего хостера отличается от стандартного облачного образа.
- **Версии с 2026.10.8 по 2026.10.17 не могли завершить настройку на облачном образе
  Ubuntu 24.04.** Они останавливались на переключении SSH и откатывались: доступ не
  терялся, но настройка не доводилась до конца. systemd считал службу SSH остановленной,
  хотя её процесс продолжал слушать порт, а скрипт не трогал этот процесс как главный у
  службы — так что единственный демон, который должен был уйти, остался на порту 22. CI
  воспроизводит это состояние — `systemctl enable ssh.service` при работающей службе,
  запущенной через сокет, — в одних прогонах и не воспроизводит в других. Он же показал
  ловушку в очевидном исправлении: если послать сигнал этому процессу, пока systemd
  считает службу остановленной, PID 1 зависает. Теперь скрипт сначала останавливает sshd и
  только потом переключает службы, приводит учёт systemd в порядок, если такое состояние
  уже есть, и читает результат из таблицы сокетов. Последний полный прогон с чистого образа был
  до этого на версии 2026.10.7. С тех пор версия 2026.10.19 прошла с чистого образа до конца,
  включая sshd, запущенный через сокет. Этот прогон шёл в новом порядке — сначала остановка
  sshd, потом переключение служб — и в сломанное состояние не попал, так что ветка, которая
  чинит его, когда оно уже есть, по-прежнему проверена только в CI.
- **Живые прогоны — на одном сервере** (Ubuntu 24.04, KVM): полная настройка с чистого
  образа, уведомления в Telegram, `--check`. Эти прогоны нашли девять вещей, которые пропустил
  CI, — ложный провал в проверке, служебные строки журнала о поиске ключа, принятые за
  входы, два уведомления на одно подключение у клиентов, открывающих второе соединение,
  потерю строк в `journalctl -f -n 0`, файлы, созданные нечитаемыми из-за собственной
  `UMASK 027` скрипта, возврат ответа на ping из-за UFW, sshd, оставшийся на старом порту при
  переключении, apport, при каждой загрузке снова разрешающий дампы привилегированных
  программ, и системный файл sysctl, который после нашего возвращал `fs.protected_fifos`
  к 1; каждая теперь воспроизводится в CI. Уведомление о падении службы
  проверено только в CI — на юните, который действительно падает, с заменителем Bot API.
- **Пути, по которым не прошёл ни один живой прогон, найдены чтением кода** строка за
  строкой и теперь покрыты тестами: повторный запуск через `sudo harden` заканчивался
  ошибкой прямо перед итоговым отчётом; запуск из консоли хостера, до первого
  подключения по SSH, останавливался на определении текущего порта; cloud-init, который
  установлен, но никогда не запускается, ожидался 45 минут; неудачная установка CrowdSec
  или порт, который UFW отказался открыть, обрывали всю настройку на середине; ключ
  приклеивался к последней строке `authorized_keys`, если файл не кончался переводом
  строки. То, что такое там было, показывает цену непроверенного пути — см. первый пункт
  этого списка.
- **Отказ отвечать на ping — маскировка, а не защита.** Сервер пропадает из проверок
  пингом, но сканирование портов находит его точно так же. Практический смысл — VPN-сервер:
  детекторы вроде 2ip сравнивают время пинга до вашего адреса с задержкой, измеренной из
  браузера («двусторонний пинг»), и без ответа этой проверке нечего измерять. Остальные
  признаки остаются — прежде всего то, что адрес принадлежит хостинг-провайдеру. Заодно «слепнет» всё, что
  проверяет сервер пингом, — в том числе мониторинг некоторых хостеров, который сочтёт его
  упавшим, — поэтому по умолчанию это выключено. Игнорируются только echo-запросы;
  ICMP, нужный для определения MTU и для IPv6, не затрагивается. Настройка пишется в два
  места — в отдельный файл sysctl и в `sysctl.conf` самого UFW: UFW применяет его при
  каждом запуске и иначе включает ответ на ping обратно.
- **Telegram видит ваши уведомления.** В сообщениях есть имя сервера и IP-адреса входов, и
  они проходят через серверы Telegram. Любой, у кого есть root на сервере, может прочитать
  токен бота и писать в этот чат от его имени — заведите бота только для этого сервера.
- **Docker обходит UFW.** Опубликованные порты контейнеров доступны, что бы ни говорил UFW.
  Публикуйте как `-p 127.0.0.1:8080:80` или используйте `ufw-docker`.
- **Проброс портов по SSH выключен**, из-за этого не работает и VS Code Remote-SSH.
  Поставьте `AllowTcpForwarding local` (и при необходимости `MaxSessions 10`) в
  `/etc/ssh/sshd_config.d/00-hardening.conf`, затем `sudo systemctl restart ssh`.
- **IP из белого списка пользуется доверием** fail2ban, CrowdSec и лимита. Если ваш IP
  динамический, тем же доверием получит и следующий его владелец — но ключ ему всё равно
  нужен.
- **Веб-консоли хостера** после блокировки root нужен пароль нового пользователя.
- **CrowdSec ставится из репозитория разработчика**, а значит, приходится доверять его
  ключу подписи. Чужие скрипты не запускаются: репозиторий подключает сам harden.sh,
  ключ принимается, только если его отпечаток — `6A89E3C2 303A901A 889971D3 376ED532
  6E93CD0C` (сверен с packagecloud.io, keyserver.ubuntu.com и keys.openpgp.org), а apt
  закреплён так, что оттуда можно поставить только `crowdsec` и
  `crowdsec-firewall-bouncer-nftables` — даже взломанный репозиторий не подсунет новый
  openssh или sudo. Если разработчик сменит ключ, CrowdSec будет пропущен, пока отпечаток
  здесь не обновят; CI проверяет его при каждом пуше.
- **Набор правил аудита загружается целиком** из `/etc/audit/rules.d`. Файлы правил,
  которые там уже были, сохраняются и загружаются вместе с нашими; правила, введённые
  через `auditctl` и нигде не сохранённые, после перезагрузки правил пропадают — как и
  после любого перезапуска.
- **Белый список IP действует только для jail'ов SSH.** Jail'ы, которые вы добавите сами,
  работают с настройками fail2ban по умолчанию — backend, действие, срок бана — и про
  IP из белого списка не знают.
- **USB-накопители отключены** — на VPS это не важно, на физическом сервере заметно.
  На физическом сервере итоговый отчёт об этом говорит и подсказывает, как вернуть.
- **Советы Lynis, которые не приняты:** отдельные разделы `/home` `/tmp` `/var` (только
  при установке ОС), пароль на GRUB (мешает консоли хостера), AIDE и антивирусы (медленно,
  шумно, ложные срабатывания), принудительная смена паролей (современные рекомендации NIST
  против), отправка логов на удалённый сервер (нужен второй сервер),
  `kernel.modules_disabled=1` (firewall и VPN подгружают модули позже). `dccp`, `sctp`, `rds`
  и `tipc` отключены через `install … /bin/false`; Lynis признаёт только `/bin/true` и
  поэтому продолжает их предлагать.
